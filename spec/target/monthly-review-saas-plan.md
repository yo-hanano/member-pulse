# 月謝制スクール向け月次経営レビュー SaaS 仮説

この文書は、個人プロダクトとして検討している月謝制スクール向け SaaS の事業仮説、MVP、拡張条件を整理する。

現時点の結論は、日常業務を置き換える運営システムではなく、月末または月初に使う月次経営レビュー SaaS として始めること。

プロダクト名の仮称は `MemberPulse` とする。

ただし、海外に同名の会員管理 / 会員エンゲージメント系サービスが存在するため、本番公開前に商標、ドメイン、同名サービス、国内利用状況を再確認する。

同名リスクを避ける場合の代替候補は `MonthlyPulse` とする。

## 1. 目的

個人プロダクトとして、まずは副業で年 200 万円前後の安定売上を目指す。

軌道に乗る場合は独立も視野に入れるが、初期段階では次の条件を優先する。

- 個人で開発、運用できる
- 営業や導入支援を重くしない
- セルフサーブで試しやすい
- 継続課金にしやすい
- サポート負荷を抑えられる

想定する運用負荷は、月 10〜20 時間程度とする。

## 2. 前提と制約

D2C / EC 領域は現在の業務と競合または利益相反になる可能性があるため、直接のターゲットにはしない。

一方で、D2C マーケティング支援システムで得た次の知見は、抽象化して別領域へ転用できる可能性がある。

- 目標と実績のギャップ分析
- KPI ツリーによる要因分解
- CPA / CPO などの広告効率指標
- LTV や継続率を踏まえた判断
- 月次レポートによる意思決定支援
- 改善施策と検証指標の紐づけ

ただし、会社固有のコード、ロジック、顧客データ、業務ノウハウをそのまま流用しない。

## 3. ターゲット仮説

初期ターゲットは、季節要因の少ない大人向け月謝制スタジオにする。

広い「習い事」ではなく、季節要因が比較的小さく、継続課金、会員、問い合わせ、体験、入会、退会が毎月発生する事業に絞る。

初期ターゲットの条件は次の通り。

- 大人向けである
- 大人向けの月謝制スタジオ、会員制スクール、会員制レッスンである
- 1〜3 店舗程度である
- 会員 50〜300 人程度である
- 月商 50 万〜300 万円程度である
- オーナーまたは店長が数字を見る
- Excel、スプレッドシート、会計ソフト、予約システムなどを併用している
- 月次の振り返りや広告費判断を感覚で行っている

初期ターゲットから外すものは次の通り。

- 学習塾、受験塾
- 子ども向け習い事
- 発表会、進級、講習などの季節要因が強い業種
- 予約、振替、請求、会員アプリの置き換えを最初から求める事業者

対象例は、ヨガ、ピラティス、パーソナルジム、ダンス、英会話などとする。

ただし、初期訴求では「月謝制スタジオ向け」と表現し、ヨガ / ピラティスは対象例として扱う。

## 4. プロダクトの位置づけ

このプロダクトは、日常業務ツールではなく、月次経営レビューの道具として位置づける。

予約、出欠、請求、会員アプリ、インストラクター管理を置き換える運営システムにはしない。

想定コピーは次の通り。

> 月次の実績を入力するだけで、利益・会員数・広告費の見直しポイントがわかる、月謝制スタジオ向け経営レビュー SaaS。

外向きには、AI 経営コーチではなく、KPI 逆算レポートまたは月次経営レビュー SaaS として見せる。

AI 的な支援を使う場合でも、価値の中心は会話ではなく、毎月のレポートと実行計画に置く。

## 5. 中核価値

中核価値は、目標と実績のギャップを分解し、今月の重要成功要因を最大 3 つ提示すること。

単なるダッシュボードではなく、次の問いに答える。

- 何が未達要因か
- どの KPI を改善すべきか
- どの打ち手を優先すべきか
- 来月何を検証するか
- ピボットや商品設計の見直しが必要か

月次レポートの主役は「今月の重要成功要因 最大 3 つ」とする。

各重要成功要因には、次の情報を紐づける。

- 関連 KPI
- 未達ギャップ
- 推奨アクション
- 検証指標

## 6. 初期入力項目

MVP の入力頻度は、月末または月初の月 1 回を基本とする。

週次、日次の運営記録は初期必須にしない。将来、月中の着地見込みを扱う場合も、予約や問い合わせ管理の全面機能ではなく、月次レビューの補助として扱う。

最小入力は次の通り。

- 月初会員数
- 月末会員数
- 新規問い合わせ数
- 体験予約数
- 体験実施数
- 入会数
- 退会数
- 総売上
- 月謝売上
- その他売上
- 平均月謝
- 広告費
- 変動費
- 固定費
- 本部経費

売上粒度は次の通り。

- 総売上
- 月謝売上
- その他売上
- 平均月謝

会員数は、月末会員数を主入力とする。月初会員数は前月末から自動設定し、月初会員数 + 入会数 - 退会数 と月末会員数が合わない場合は警告のみ出す。入力保存は妨げない。

問い合わせ、体験、入会は月次集計値として入力する。問い合わせ管理や体験予約管理を必須機能にはしない。

CPA / CPO は次のように扱う。

- CPA: 広告費 ÷ 問い合わせ数
- CPO: 広告費 ÷ 入会数

広告投資判断では、粗利 LTV と限界 CPO も扱う。

- 月次退会率: 退会数 ÷ 月初会員数
- LTV 計算用退会率: 直近 3 か月平均退会率
- 退会率下限: 1%
- 平均継続月数: 1 ÷ LTV 計算用退会率
- 月謝 1 会員あたり粗利: 平均月謝 - 会員連動変動費 - 月謝売上率連動変動費
- 粗利 LTV: 月謝 1 会員あたり粗利 × 平均継続月数
- 限界 CPO: 粗利 LTV × 許容広告投資率

限界 CPO 判定は、実績 CPO ÷ 限界 CPO で行う。

- 安全: 70% 以下
- 注意: 70% 超〜100%
- 危険: 100% 超

## 7. PL の位置づけ

PL は扱う。ただし、会計ソフトの代替にはしない。

目的は、税務や会計処理ではなく、経営判断用の簡易 PL とする。

扱わないものは次の通り。

- 仕訳
- 税務申告
- 消費税計算
- 決算書作成
- 銀行連携
- 会計ソフト連携
- 厳密な勘定科目管理

簡易 PL で見たい判断は次の通り。

- 売上未達なのか
- 広告費を増やす余地があるのか
- 人件費率が高すぎるのか
- 固定費に対して在籍数が足りないのか
- 利益を残すには単価を上げるべきか
- 集客より退会抑制を優先すべきか

PL は、全体 PL とスタジオ別 PL の両方を見る。

費用は次の区分で扱う。

- 広告費
- スタジオ直接変動費
- スタジオ直接固定費
- 本部経費

変動費と固定費はマスタ登録し、月次 PL に反映する。

変動費マスタは次の計算方式を持つ。

- 売上率: 月謝売上または総売上 × n%
- 会員数連動: 月末会員数 × n 円
- 実績入力: 月次で金額を直接入力

固定費マスタは、家賃、システム固定費、保険、税理士費用などの毎月発生する費用を登録し、月次入力では必要に応じて上書きする。

本部経費は売上比率でスタジオ別に按分する。

広告費は PL に反映するが、CPO / 限界 CPO 判断用に独立管理する。広告費は全体広告費と任意のスタジオ別広告費を扱う。

全体 PL は、売上、粗利、営業利益の段階で表示する。

- 総売上
  - 月謝売上
  - その他売上
- 変動費
- 粗利
- 広告費
- 固定費
- 本部経費
- 営業利益

広告費は営業利益計算に含める。ただし広告費は CPA / CPO / LTV / 限界 CPO 判断の主役でもあるため、広告 KPI セクションでも独立表示する。PL と広告 KPI で同じ広告費を二重計上しない。

スタジオ別 PL は、月次レビュー内の 1 セクションとして扱う。独立した PL 分析画面は MVP では作らない。

スタジオ別 PL セクションは、比較テーブルと要約カードで構成する。

比較テーブルの列は次の通り。

- スタジオ名
- 売上
- 広告費
- 変動費
- 固定費
- 直接利益
- 本部経費配賦
- 配賦後営業利益
- 利益率
- CPO
- 限界 CPO
- 月末会員数
- 入会数
- 退会数

本部経費配賦は、通常表示では配賦額と配賦後営業利益を見せる。計算根拠は行の展開表示にする。

展開表示で見せる根拠は次の通り。

- スタジオ売上
- 全体売上
- 売上構成比
- 本部経費総額
- 配賦額

スタジオ別 PL の要約カードは、問題のあるスタジオだけ最大 3 件表示する。

要約対象は次の通り。

- 配賦後営業利益が赤字
- 利益率が目標未達
- CPO が限界 CPO 超過
- 退会率が許容退会率超過
- 会員数が目標未達
- 前月比で利益が大きく悪化

スタジオ別広告費は次のように扱う。

- スタジオ指定広告費: そのスタジオへ直接計上
- スタジオ未指定広告費: 本部広告費として売上比率で配賦
- 全体 PL: すべての広告費を合算
- スタジオ別 PL: 直接広告費 + 配賦広告費

スタジオ別限界 CPO は、スタジオ別の月謝 1 会員あたり粗利をベースに計算する。

```text
スタジオ別月謝 1 会員あたり粗利
  = スタジオ平均月謝
    - スタジオ会員連動変動費
    - スタジオ月謝売上率連動変動費

スタジオ別粗利 LTV
  = スタジオ別月謝 1 会員あたり粗利
    × スタジオ別平均継続月数

スタジオ別限界 CPO
  = スタジオ別粗利 LTV
    × 許容広告投資率
```

固定費や本部経費は、限界 CPO には含めない。広告で 1 人増えたときの獲得許容額は、まずその会員が生む月次粗利と継続月数で見る。固定費や本部経費は、PL と利益率で別途判断する。

## 8. 入力支援

月次実績や PL 項目を毎月洗い出すことは負担になる。

初期 MVP では、自動取得ではなく、入力しやすくする支援を優先する。

候補は次の通り。

- 前月値コピー
- 概算入力
- 未確定フラグ
- 数字の探し方ガイド
- 平均月謝と在籍数から売上を概算
- 入会数、退会数から在籍数を補助計算
- 既存 Excel からのコピペ入力
- スマートフォンでも月末に短時間で入力できる画面

問い合わせ数が不明な場合は、未計測として扱い、次月から計測対象にする。

既存の `juku-ops` CRM 機能は、月次レビュー入力の任意補助として使う。

CRM は主機能として見せない。表向きの主機能は月次経営レビューとする。

CRM を使う場合、次の集計に使う。

- 問い合わせ数: `lead.inquiry_at`
- 体験予約数 / 体験実施数: `schedule_event`
- 入会数: `lead.status = enrolled` または会員作成
- 月末会員数: `student.status`
- 契約月謝: `contract.monthly_fee` 相当

既存モデルの表示用語は月謝制スタジオ向けに置き換える。

- 生徒: 会員
- 来塾 / 体験授業: 体験レッスン
- 校舎 / 教室: スタジオ
- 講師 / 教師: インストラクター
- 契約: 月額プラン契約
- 保護者: 基本非表示または緊急連絡先

退会数は、月次実績入力で手入力できるようにしつつ、軽量会員台帳を使う場合は会員ステータスと契約履歴から集計できるようにする。返金、請求停止、決済連携などは後回しにする。

CRM 補助機能は、別メニューの任意機能として置く。月次入力ウィザードの中に CRM 操作を直接入れない。

月次入力ウィザードでは、CRM からの集計値と今回採用する入力値を分けて表示する。

- CRM 集計値: 参考表示
- 今回の入力値: 初期値として CRM 集計値をコピー
- ユーザー上書き: 可能
- 差分がある場合: 警告のみ表示

CRM 集計値の対象は次の通り。

- 問い合わせ数
- 体験予約数
- 体験実施数
- 入会数
- 月末会員数
- 平均月謝

MVP の CRM 補助機能は、問い合わせ、体験、入会、会員台帳の軽量管理まで扱う。

作るものは次の通り。

- 問い合わせ登録
- 体験予定登録
- 体験実施 / 未実施
- 入会 / 失注
- `lead` から `member` への入会変換
- 連絡先つき軽量会員台帳
- 月額プラン契約履歴
- 休会
- 退会

作らないものは次の通り。

- 予約枠管理
- 出席履歴
- 決済
- 請求履歴
- 会員アプリ
- LINE 連携
- リマインド通知
- 契約書管理
- 詳細な同意書管理
- 健康情報管理

軽量会員台帳は、会員対応を主目的にするのではなく、入会、退会、継続、LTV を正しく集計するための補助機能として位置づける。

`lead` から `member` へ入会変換する導線を作る。二重入力を避けるため、入会確定時に `member` と `membership_subscription` を作成する。

入会後も `lead` は残し、`member` から `lead_id` で参照する。

- `lead.status = enrolled`
- `member.lead_id = lead.id`
- `trial_session.lead_id` は履歴として保持
- `member` 作成時に氏名、連絡先、流入元などを引き継ぐ

退会時は、`member` の状態と `membership_subscription` の終了情報を両方更新する。

- `member.status = resigned`
- `member.resigned_at`
- `member.resignation_reason_code`
- `member.resignation_note`
- 現在有効な `membership_subscription.end_date`
- `membership_subscription.status = ended`

休会は MVP に含める。ただし集計上は在籍会員と分ける。

- `member.status = active / paused / resigned`
- 休会者は月末会員数の内訳に表示
- LTV 計算の退会数には含めない
- 月謝売上には含めない。休会費がある場合だけ含める
- `membership_subscription.status = paused` を許容する

会員台帳の MVP 項目は次の通り。

必須項目:

- 氏名
- 所属 `location`
- `status`
- 入会日

任意項目:

- 電話番号
- メール
- LINE 表示名 / メモ
- 住所
- 生年月日
- 流入元
- 退会日
- 退会理由
- 備考

月額プラン金額は `member` ではなく `membership_subscription` 側に持たせる。

退会理由は選択式 + メモで持つ。

初期の退会理由候補は次の通り。

- 料金
- 通う時間がない
- 効果を感じない
- 予約が取りにくい
- スタジオ / 立地
- インストラクター相性
- 体調
- 引っ越し
- 他社へ移行
- 不明
- その他

## 9. MVP で作るもの

初期 MVP で作るものは次の通り。

- アカウント登録、ログイン
- 事業プロフィール
- 目標設定
- 月次実績入力
- 広告 KPI 入力
- 簡易 PL 入力
- 変動費マスタ
- 固定費マスタ
- 本部経費の売上比率按分
- 全体 PL
- スタジオ別 PL
- 粗利 LTV
- 限界 CPO
- KPI 逆算
- ギャップ分解
- 重要成功要因 最大 3 つ
- 推奨アクション
- 検証指標
- 月次履歴
- 画面表示
- 印刷 / PDF 向け表示
- 任意の簡易 CRM 入力補助

目標設定は、年間目標と簡単な前提から月別目標を自動生成する。必要に応じて月別上書きできるようにする。

初期目標項目は次の通り。

- 年間売上目標
- 目標営業利益
- 目標月末会員数
- 平均月謝
- 許容退会数または退会率
- 広告費上限

ギャップ分解の優先順位は次の通り。

1. 営業利益
2. 月末会員数
3. 月商
4. 入会数
5. 退会数
6. CPO / 限界 CPO

重要成功要因の判定は、ルールベース中心で行う。生成 AI を使う場合も文章補助に留める。

判定対象は次の通り。

- 会員数未達
- 入会数不足
- 問い合わせ不足
- 体験化率不足
- 入会率不足
- 退会過多
- CPO 超過
- 限界 CPO 接近
- 粗利率低下
- 固定費過多
- スタジオ別利益悪化

目標自動生成では、毎月均等配分をデフォルトとし、任意で月次成長率を設定できるようにする。

初期入力項目は次の通り。

- 年間売上目標
- 年間営業利益目標
- 年度末会員数目標
- 現在会員数
- 平均月謝
- 許容退会率
- 想定 CVR
- 広告費上限
- 許容広告投資率

月別の会員数目標は、現在会員数から年度末会員数まで線形に増やす。

```text
月別目標月末会員数
  = 現在会員数
    + (年度末会員数 - 現在会員数)
      × 経過月数 / 残月数
```

目標入会数は、目標純増数と許容退会数から逆算する。

```text
目標純増数
  = 当月目標月末会員数
    - 前月目標月末会員数

許容退会数
  = 前月目標月末会員数
    × 許容退会率

目標入会数
  = 目標純増数
    + 許容退会数
```

端数は切り上げる。

目標問い合わせ数は、目標入会数と想定 CVR から逆算する。

```text
目標問い合わせ数
  = 目標入会数
    ÷ (体験予約率 × 体験実施率 × 入会率)
```

月別売上目標は、月謝売上を会員数と平均月謝から作り、年間売上目標との差分をその他売上に配分する。

```text
月謝売上目標
  = 月別目標月末会員数
    × 平均月謝

年間月謝売上目標
  = 月別月謝売上目標の合計

その他売上年間目標
  = 年間売上目標
    - 年間月謝売上目標

その他売上月別目標
  = その他売上年間目標
    ÷ 12
```

年間売上目標が年間月謝売上目標を下回る場合は、入力前提が矛盾しているため警告を出す。この場合、その他売上年間目標は 0 に丸める。

```text
その他売上年間目標
  = max(0, 年間売上目標 - 年間月謝売上目標)
```

月別営業利益目標は、年間営業利益目標を 12 等分する。月別売上目標に対する目標利益率は参考表示する。

広告費上限は、年間広告費上限を 12 等分する。ただし、限界 CPO から見た採算広告費上限も参考表示する。

```text
月別広告費上限
  = 年間広告費上限
    ÷ 12

採算広告費上限
  = 目標入会数
    × 限界 CPO

実務上の広告費目安
  = min(月別広告費上限, 採算広告費上限)
```

## 14. 月次レビュー状態管理

月次レビュー入力は、入力ウィザードからレポート生成へ進む導線にする。

入力ウィザードのステップは次の通り。

1. 対象月とスタジオ選択
2. 会員数: 月初、月末、入会、退会
3. 集客: 問い合わせ、体験予約、体験実施
4. 売上: 総売上、月謝売上、その他売上、平均月謝
5. 広告費: 全体 / スタジオ別広告費
6. 費用: 変動費、固定費、本部経費の確認 / 上書き
7. 確認: 自動計算 KPI と警告
8. レポート生成

状態は次の 4 つとする。

- 未開始
- 入力中
- レビュー生成済み
- 確定済み

レビュー生成済みと確定済みは分ける。レビュー生成済みはレポートを見られるが数字は編集可能な状態、確定済みは月次履歴としてロックされた状態とする。

確定済み月を修正する場合は、確定解除して入力中に戻し、編集、レビュー再生成、再確定の順で扱う。MVP では監査ログは作らない。

確定済み月は、翌月の月初会員数、前月コピー、直近 3 か月平均退会率の計算基準に使う。

月次レビューは、生成時点の計算結果をスナップショット保存する。費用マスタ、配賦ルール、退会率下限、広告投資率などを後で変更しても、過去レポートが勝手に変わらないようにする。

スナップショット保存する内容は次の通り。

- 入力値
- 主要 KPI
- PL 計算結果
- LTV / 限界 CPO
- 重要成功要因 最大 3 つ
- 推奨アクション
- 使用した設定値のコピー

推奨アクションは、テンプレート生成後にユーザーが編集できるようにする。編集後の文言をスナップショットに保存し、再生成時は上書きするか確認する。

## 15. 重要成功要因の判定ルール

重要成功要因は、ルールベースで判定する。生成 AI を使う場合も、根拠となる数値判定はルールベースで行い、文章補助に留める。

### 15.1 優先順位

重要成功要因は最大 3 つに絞る。

優先順位は、営業利益への影響額を主、会員数への影響を副として決める。

MVP では次の順で優先する。

1. 営業利益への影響額が大きいもの
2. 月末会員数未達に直結するもの
3. CPO が限界 CPO を超えているもの
4. スタジオ別で赤字を生んでいるもの
5. 前月から悪化しているもの

### 15.2 営業利益未達の分解

最初の判定ツリーは、営業利益未達の分解から作る。

- 営業利益未達
  - 売上不足
  - 広告費過多
  - 変動費過多
  - 固定費過多
  - 本部経費配賦後の特定スタジオ赤字

### 15.3 売上不足の分解

売上不足は、月謝売上不足を主、その他売上不足を副として扱う。

- 総売上不足
  - 月謝売上不足
    - 月末会員数不足
    - 平均月謝不足
  - その他売上不足

月謝制スタジオの経営安定性は月謝売上に依存するため、その他売上不足は副次要因として扱う。

### 15.4 月末会員数不足の分解

月末会員数不足は、次の順で分解する。

1. 入会不足
2. 退会過多
3. 月初会員数不足

月初会員数不足は過去の積み上げ不足であるため、当月の重要成功要因としては入会不足と退会過多を優先する。

### 15.5 入会不足の分解

入会不足は、ファネルの上流から順に見る。

- 問い合わせ数
- 体験予約数
- 体験実施数
- 入会数

派生 KPI は次の通り。

- 体験予約率: 体験予約数 ÷ 問い合わせ数
- 体験実施率: 体験実施数 ÷ 体験予約数
- 入会率: 入会数 ÷ 体験実施数
- 問い合わせ入会率: 入会数 ÷ 問い合わせ数

画面上は、CVR という表現よりも体験予約率、体験実施率、入会率という業務用語を優先する。

問い合わせは、体験予約前の見込み客接点と定義する。Web フォーム、LINE 問い合わせ、電話、Instagram DM、店頭問い合わせ、紹介経由の連絡を含める。体験予約だけが直接入る導線では、問い合わせ数 = 体験予約数として扱えるようにする。

問い合わせ不足は、目標問い合わせ数とのギャップで判定する。

- 問い合わせ数 < 目標問い合わせ数: 問い合わせ不足
- 問い合わせ不足 かつ CPO が安全ライン: 広告増額余地あり
- 問い合わせ不足 かつ CPO が注意 / 危険: 広告増額より導線改善を優先

目標問い合わせ数は、目標入会数と想定 CVR から逆算する。

```text
目標問い合わせ数 = 目標入会数 ÷ (体験予約率 × 体験実施率 × 入会率)
```

想定 CVR は、過去 3 か月実績を優先し、実績がなければ初期値を使う。ユーザーは目標 CVR を上書きできる。

初期 CVR は次の通り。

- 問い合わせ → 体験予約率: 70%
- 体験予約 → 体験実施率: 80%
- 体験実施 → 入会率: 50%
- 問い合わせ → 入会率: 28%

### 15.6 退会過多の判定

退会過多は、許容退会率と比較して判定する。

- 当月退会率 > 許容退会率: 当月退会過多
- 直近 3 か月平均退会率 > 許容退会率: 構造的な退会過多
- 退会数が目標会員数達成に必要な許容退会数を超過: 会員数未達要因

許容退会率の初期値は月次 3% とする。ユーザーは上書きできる。

LTV 計算では、直近 3 か月平均退会率を使う。ただし退会率が低すぎる場合は、下限退会率 1% を使う。

### 15.7 平均月謝不足の判定

平均月謝不足は、目標平均月謝との比較で判定する。

- 平均月謝 < 目標平均月謝: 平均月謝不足

ただし重要成功要因に上げるのは、月謝売上未達への影響額が大きい場合だけとする。

MVP では、値上げ、上位プラン比率、割引、休会、低単価プラン比率などの詳細分解までは行わない。推奨アクションは「割引、低単価プラン、上位プラン比率を確認する」程度に留める。

### 15.8 広告費過多と CPO の判定

広告費過多は、実績 CPO と限界 CPO の比較を主判定にする。

- CPO > 限界 CPO: 広告費過多 / 獲得効率危険
- CPO > 限界 CPO × 70%: 注意
- 広告費 > 広告費上限 かつ CPO 注意以上: 広告費抑制候補
- 問い合わせ不足 かつ CPO 安全: 広告増額余地あり

CPO が悪い場合は、CPA と問い合わせ入会率に分解する。

- CPA 悪化: 広告費 ÷ 問い合わせ数が高い
- 問い合わせ入会率悪化: 入会数 ÷ 問い合わせ数が低い

問い合わせ入会率の悪化は、体験予約率、体験実施率、入会率に分解する。

### 15.9 変動費過多の判定

変動費過多は、実績変動費とマスタから算出した想定変動費の差分で判定する。

- 実績変動費率 = 変動費 ÷ 対象売上
- 実績変動費率 > 設定変動費率 + 許容幅: 変動費過多
- 影響額 = 実績変動費 - 想定変動費

売上が伸びれば変動費額も増えるため、金額だけではなく率と想定差分で見る。

### 15.10 固定費過多の判定

固定費過多は、固定費超過と固定費負担過大の 2 軸で判定する。

- 固定費超過: 実績固定費 > マスタ / 予算固定費
- 固定費負担過大: 固定費 ÷ 売上 が目標固定費率を超過

重要成功要因に出すときは、営業利益未達への影響額が大きい方を優先する。

### 15.11 スタジオ別赤字の判定

スタジオ別赤字は、本部経費配賦後営業利益で判定する。

スタジオ別 PL では次の利益段階を並べる。

- スタジオ直接利益
- 本部経費配賦額
- 配賦後営業利益

判定は次の通り。

- 配賦後営業利益 < 0: スタジオ赤字
- 配賦後営業利益率 < 目標利益率: 利益率低下
- 直接利益は黒字だが配賦後赤字: 本部経費負担の見直し候補

## 16. D2C 支援システム参照時の確認観点

D2C 支援システムを参照できる状態になったら、次の観点で流用可能性を判断する。

1. D2C システムにある概念のうち、月謝制スクールに転用できるもの
2. 転用してはいけない、会社固有または競合リスクのあるもの
3. KPI / PL / レポート生成で流用できる設計パターン
4. MVP の入力項目と画面構成
5. プロダクトの最小スコープ再定義

流用候補は、コードや固有ロジックではなく、公開可能な抽象パターンに限定する。

現時点で転用候補とする抽象パターンは次の通り。

- 固定費設定
- カスタム変動費設定
- 本部経費配賦
- 広告費の独立管理
- CPA / CPO
- LTV / 限界 CPO
- 全体 PL / 拠点別 PL
- 目標と実績のギャップ分解
- 重要成功要因の抽出

## 17. 新リポジトリ前提のデータモデル方針

実装は、新しいリポジトリで作る前提とする。

既存の `juku-ops` は参考実装として使うが、塾向けの `student`、保護者、学校、学年、授業、請求などの文脈は持ち込まない。

テーブル名は、特定業種に寄せすぎず、会員ビジネス全般へ横展開しやすい汎用名にする。

主要テーブル候補は次の通り。

| テーブル | 役割 |
| --- | --- |
| `location` | スタジオ、店舗、教室、ジムなどの拠点 |
| `member` | 会員 |
| `lead` | 見込み客、問い合わせ |
| `trial_session` | 体験レッスン、体験セッション |
| `membership_plan` | 月額プラン |
| `membership_subscription` | 会員のプラン契約履歴 |
| `monthly_review` | 事業全体の月次レビュー親 |
| `monthly_review_location` | 拠点別の月次入力値、集計値 |
| `monthly_review_snapshot` | 生成済み全体レビューのスナップショット |
| `monthly_review_location_snapshot` | 生成済み拠点別レビューのスナップショット |
| `cost_item` | 固定費、変動費、本部経費を表現する費用マスタ |
| `ad_spend` | 広告費 |

`location` は、スタジオ、店舗、教室、ジムのどれにも使える拠点名として採用する。`branch` は支店感が強いため避ける。

`member` は、月謝制スタジオ、ジム、英会話、会員制スクールに横展開しやすい会員モデルとして採用する。`student` はスクール寄り、`customer` は広すぎるため使わない。

`lead` は、問い合わせ、体験前、入会前の見込み客を表すモデルとして採用する。

`trial_session` は、体験レッスン / 体験セッションの予定と実施状態を表す。`trial` だけだと無料期間や試用契約と誤解しやすく、`appointment` は予約全般に広がりすぎるため使わない。

`membership_plan` は、月額会員制のプランを表す。`plan` だけだと月次計画と衝突し、`course` はスクール寄りになるため使わない。

会員の契約履歴は `membership_subscription` として持つ。現在値だけを `member` に持たせると、プラン変更、値上げ、休会、退会、再入会で過去月の平均月謝や LTV が壊れるためである。ただし、請求管理や決済管理までは扱わない。

`membership_subscription` の最小項目は次の通り。

- `member_id`
- `membership_plan_id`
- `start_date`
- `end_date`
- `status`
- `monthly_fee`
- `note`

費用マスタは `cost_item` に統一する。固定費、変動費、本部経費をテーブル分割せず、費用タイプ、適用範囲、計算方式で表現する。

`cost_item` の主な軸は次の通り。

- `cost_type`: `fixed` / `variable`
- `scope`: `location_direct` / `head_office`
- `calculation_method`: `fixed_amount` / `revenue_rate` / `member_count` / `manual`
- `amount`
- `rate`
- `active`

月次レビューは、入力値と生成結果を分ける。

- `monthly_review`: 対象月、状態、全体入力値、上書き値
- `monthly_review_location`: 拠点別の入力値、集計値
- `monthly_review_snapshot`: KPI、PL、LTV、重要成功要因、推奨アクション、使用設定コピー
- `monthly_review_location_snapshot`: 拠点別 KPI、PL、LTV、配賦後利益、判定結果

入力途中の値と生成済みレポートのスナップショットはライフサイクルが違うため、同じテーブルに混ぜない。

## 18. 技術スタック方針

新リポジトリのアーキテクチャは、既存の `juku-ops` / `alcos-poc` 系の分離構成を踏襲する。

基本構成は次の通り。

- Frontend: React Router v7
- BFF: Hono
- Backend: Quarkus GraphQL
- DB: PostgreSQL
- Migration / codegen: Liquibase + jOOQ
- Package manager: pnpm
- Formatter / linter: Biome

UI ライブラリは Mantine v9 に固定する。

理由は次の通り。

- 月次レビュー入力ウィザードに必要な Stepper、フォーム、テーブル、モーダル、日付 / 月選択、通知、集計カードが揃っている
- `markeman` のプランニングガイドが Mantine で実装されており、入力ガイドやステップ管理の設計資産を参考にしやすい
- HeroUI よりも業務 SaaS の密な入力、比較表、PL 表示に向いている
- shadcn は見た目と所有感はあるが、Radix 系依存と自前 UI 部品の保守が増え、個人運営 MVP には重くなりやすい

`juku-ops` の HeroUI 実装は参考にしつつ、新リポジトリでは採用しない。

`alcos-poc` の shadcn 試作は、UI の構成やレイアウトの参考に留める。
